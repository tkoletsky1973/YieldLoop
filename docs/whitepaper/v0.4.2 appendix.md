## Appendix A — System State Machine & Cycle Finality

This appendix defines the authoritative state machine governing vault behavior, accounting cycles,
settlement, and finality within YieldLoop.

This state machine enforces **accounting finality** while preserving **standing user intent**.
Cycles delimit accounting periods. They do **not** revoke strategy mandates or force asset changes.

Any behavior not explicitly permitted by this state machine is invalid by definition.

---

### A.1 Core Concepts

- **Accounting Cycle**: A time-bounded window used exclusively to measure, settle, and finalize
  accounting outcomes.
- **Standing Execution Mandate**: A user-authorized strategy configuration that remains valid
  across accounting cycles unless explicitly modified or revoked by the user.
- **Finality**: Applies to accounting results only. Asset state and user intent are not reset by
  cycle closure.

---

### A.2 Vault States

Each user vault exists in exactly one of the following states at any time:

1. **Idle**
2. **Configured**
3. **Executing**
4. **Settling**
5. **Closed**
6. **Paused** (exceptional)
7. **Recovered** (exceptional)

States are mutually exclusive.

---

### A.3 Idle State

**Description**  
The vault holds user assets with no active accounting cycle.

**Properties**

- Assets remain fully owned by the user
- Standing execution mandate (if any) remains valid
- No accounting cycle is active
- Profit recognition is inactive
- User may modify or revoke strategy parameters
- Withdrawals are permitted unless restricted by protocol rules external to cycles

**Allowed Transitions**

- Idle → Configured
- Idle → Executing (start of a new accounting cycle under an existing mandate)
- Idle → Withdraw (no state change)

Idle does **not** imply that strategy authorization has expired.

---

### A.4 Configured State

**Description**  
The user is defining or modifying strategy parameters prior to execution.

**Properties**

- Strategy parameters are mutable
- No accounting cycle is active
- No settlement or profit recognition occurs
- Assets remain user-controlled

**Allowed Transitions**

- Configured → Idle (configuration cleared or saved without execution)
- Configured → Executing
- Configured → Withdraw

---

### A.5 Executing State

**Description**  
An accounting cycle is active and execution occurs under the standing mandate.

**Properties**

- Execution operates strictly within authorized strategy bounds
- No parameter mutation is permitted during the cycle
- Execution actions may occur
- Accounting data is accumulated but not finalized

**Allowed Transitions**

- Executing → Settling (cycle end or execution halt)

**Forbidden Actions**

- Strategy mutation
- Unauthorized capital access
- Expansion beyond authorized bounds

---

### A.6 Settling State

**Description**  
Execution has paused and accounting finalization occurs.

**Properties**

- Asset balances are snapshotted
- Accounting outcomes are calculated
- Profit is either verified or rejected
- Inventory is recorded separately
- No execution actions occur

Settlement:

- Occurs exactly once per cycle
- Is deterministic
- Cannot be skipped or repeated

**Allowed Transitions**

- Settling → Closed

---

### A.7 Closed State

**Description**  
The accounting cycle has finalized and finality is enforced.

**Properties**

- Accounting outcomes are immutable
- Profit recognition for the cycle is complete
- Fees and surplus accounting (if any) are finalized
- Inventory remains owned by the user
- Standing execution mandate remains intact

**Allowed Transitions**

- Closed → Idle (awaiting next accounting cycle)
- Closed → Executing (initiate a new accounting cycle under unchanged mandate)

Closing a cycle does **not** revoke strategy authorization.

---

### A.8 Paused State (Exceptional)

**Description**  
A system-level pause preventing the start of new accounting cycles.

**Properties**

- Standing mandates remain unchanged
- Existing asset state is unaffected
- No new Executing transitions allowed

**Allowed Transitions**

- Paused → Idle
- Paused → Configured

---

### A.9 Recovered State (Exceptional)

**Description**  
Indicates system readiness following an exceptional condition.

**Properties**

- No retroactive changes
- No settlement modification
- Prospective operation only

Recovered state exists for audit traceability.

---

### A.10 Finality Rules

Finality applies exclusively at the **Closed** state.

Once a cycle is closed:

- Accounting outcomes cannot be altered
- Settlement cannot be replayed
- Profit recognition cannot be revised

Finality does **not**:

- Force liquidation
- Invalidate asset holdings
- Revoke standing execution mandates
- Require strategy reauthorization

---

### A.11 Invalid Transitions (Explicitly Forbidden)

The following transitions are invalid under all circumstances:

- Settling → Executing
- Closed → Settling
- Any state → Parameter mutation during Executing or Settling
- Any state → Unauthorized execution beyond mandate

All invalid transitions must be rejected.

---

### A.12 Conservative Resolution Rule

If ambiguity or failure occurs during Executing or Settling:

- Execution pauses
- Settlement resolves conservatively
- Profit is rejected
- Cycle proceeds to Closed

Inventory remains unaffected.

---

### A.13 Why This State Machine Exists

This state machine enforces:

- Accounting finality without forced action
- Persistent user intent without silent mutation
- Clear responsibility boundaries
- Deterministic, auditable outcomes

Cycles close books.  
Mandates persist by user choice.  
Nothing changes unless the user says it does.

## Appendix B — Cycle Settlement Math & Valuation Rules

This appendix defines the **authoritative accounting and settlement logic** for YieldLoop.
It governs how outcomes are measured, verified, and finalized at the end of each accounting
cycle.

Settlement finalizes **accounting truth only**. It does not revoke strategy mandates, force
liquidation, or alter asset ownership.

---

### B.1 Core Principles

- Settlement applies **only** to the completed accounting cycle
- Profit recognition is binary: **verified profit** or **zero**
- Only **realized settlement assets** participate in profit verification
- Open positions are treated as **inventory**, not profit or loss
- Finality applies to accounting outcomes, not asset state

---

### B.2 Definitions

**Cycle**  
A time-bounded accounting window with a defined start, end, and single settlement event.

**Settlement Asset**  
The designated asset used to measure realized outcomes for the cycle (e.g., USDT, USDC, BNB).
The settlement asset is fixed at cycle start.

**Realized Value**  
Value actually held in the settlement asset at settlement time.

**Inventory**  
Any non-settlement asset held at cycle end, including open positions or unexited trades.

**Execution Costs**  
All costs incurred during the cycle that are attributable to execution, including gas, protocol
fees, swap fees, and other explicitly authorized expenses.

---

### B.3 Settlement Outputs

Settlement produces exactly two outputs:

#### B.3.1 Realized Settlement Outcome (Authoritative)

This output determines whether verified profit exists.

Inputs:

- `S0` — Settlement asset balance at cycle start
- `S1` — Settlement asset balance at settlement
- `C` — Total execution costs denominated in settlement asset terms

Net Result:

NR = (S1 - S0) - C

Outcome:

- If `NR > 0` → **Verified profit exists**
- If `NR ≤ 0` → **Verified profit does not exist (treated as zero)**

Only this result is authoritative for profit recognition, fee assessment, and surplus accounting.

---

#### B.3.2 Inventory Report (Non-Authoritative)

Inventory includes all assets held at cycle end that are **not** the settlement asset.

Inventory:

- Is recorded for transparency and auditability
- Is not marked to market
- Does not increase or reduce profit
- Does not constitute a recognized loss
- Remains fully owned by the user

Inventory persists beyond cycle closure and may be acted upon under the standing execution
mandate or user instruction in subsequent cycles.

---

### B.4 Profit Recognition Rules

Profit is recognized only if:

- It is realized into the settlement asset
- It survives all execution costs
- It can be deterministically calculated
- Settlement completes without ambiguity

The following do **not** count as profit:

- Unrealized gains
- Mark-to-market estimates
- Inventory value
- Temporary intra-cycle balances

Settlement prefers rejecting profit over assuming it.

---

### B.5 Fee Applicability

Platform fees apply **only** when verified profit exists.

Let:

- `P = NR` (verified profit)
- `f` = platform fee rate for the cycle

Then:

Fee = min(P × f, P)

If `NR ≤ 0`, then:

Fee = 0

Fees:

- Never apply to principal
- Never apply to inventory
- Never apply to unrealized value
- Are assessed only at settlement

---

### B.6 Deterministic Cost Accounting

Execution costs must be accounted deterministically.

Preferred order:

1. Exact on-chain receipts denominated in the settlement asset
2. Deterministic conversion using a single allowlisted on-chain price source at a fixed block
3. Explicitly defined fallback source, if primary is unavailable

Rules:

- No averaging
- No discretionary pricing
- No retroactive adjustment

If deterministic accounting is not possible, conservative resolution applies.

---

### B.7 Conservative Resolution Rule

If any required settlement input is:

- Missing
- Ambiguous
- Inconsistent
- Non-deterministic

Then:

- Verified profit is rejected
- Outcome resolves to zero
- Settlement completes
- Inventory remains unchanged

Conservative resolution applies only to profit verification, not inventory recording.

---

### B.8 Settlement Lifecycle

1. Cycle end is reached or execution halts
2. Execution pauses
3. Settlement begins
4. Balances are snapshotted
5. Costs are computed
6. Net result is calculated
7. Binary outcome is determined
8. Fees and surplus accounting (if any) are applied
9. Cycle is closed immutably

Settlement occurs exactly once per cycle.

---

### B.9 Non-Negotiable Rules Summary

- No mark-to-market profit
- No forced liquidation
- No carryover of gains or losses
- No accounting outside cycles
- No profit without realization
- Finality is absolute for accounting outcomes

Cycles close books.  
Inventory persists.  
Truth is enforced.

## Appendix C — Zero-Result Cycles, Dormancy, and Inactivity

This appendix defines all conditions under which cycles correctly resolve to zero, as well as the rules governing system dormancy and intentional inactivity.

Zero outcomes and inactivity are not failure states.  
They are required behaviors that preserve accounting truth and system integrity.

---

### C.1 Definition of a Zero-Result Cycle

A zero-result cycle is any cycle that completes settlement without verified positive surplus.

A cycle resolves to zero if:
- The net settlement outcome is zero or negative
- Execution halts before producing surplus
- Costs fully consume any gains
- Valuation ambiguity forces conservative resolution
- External dependencies fail in a non-recoverable way

Zero is a final and valid outcome.

---

### C.2 Zero Is Not a Loss Mask

Zero-result cycles:
- Do not charge platform fees
- Do not mint LOOP
- Do not trigger incentives
- Do not roll forward balances
- Do not create accounting artifacts

Zero does not imply that execution failed.
It means surplus did not survive settlement.

---

### C.3 Common Zero-Resolution Scenarios

Zero-result cycles may occur due to:
- Flat or adverse market conditions
- Slippage exceeding expectations
- Liquidity constraints
- External protocol fees
- Gas costs exceeding gains
- Strategy halt conditions
- Conservative valuation rules

All such outcomes are expected.

---

### C.4 No Carryover or Compensation

YieldLoop explicitly forbids:
- Carrying losses forward
- Offsetting future profits
- Smoothing outcomes across cycles
- Issuing compensation or rewards
- Subsidizing underperformance

Each cycle is independent.

---

### C.5 Dormant Vaults

A vault may remain dormant indefinitely.

Dormancy means:
- No execution is authorized
- Funds remain idle
- No risk is assumed
- No accounting changes occur

Dormancy is a valid long-term state.

---

### C.6 System-Wide Inactivity

The YieldLoop protocol may experience periods of low or zero activity.

System-wide inactivity:
- Does not invalidate prior results
- Does not require intervention
- Does not trigger failover behavior
- Does not require emissions or incentives

The system is designed to wait.

---

### C.7 Intentional Refusal to Execute

The system may refuse to authorize new cycles if:
- Risk conditions are unsafe
- External dependencies are unreliable
- Guardrails are violated
- Governance-imposed pauses are active

Refusal is a safety mechanism, not an error.

---

### C.8 Recovery From Inactivity

Resuming activity after dormancy:
- Requires no special process
- Does not reopen past cycles
- Does not adjust prior accounting
- Applies only to new authorizations

Inactivity leaves no residue.

---

### C.9 Zero Outcomes and User Experience

Zero-result cycles must be presented:
- Clearly
- Without stigma
- Without error framing
- Without implication of system malfunction

Users are informed that zero is a correct result.

---

### C.10 Why Zero and Dormancy Are Required

Systems that cannot tolerate inactivity or zero outcomes eventually distort truth.

YieldLoop enforces acceptance of zero so that:
- Risk remains visible
- Performance remains honest
- Growth is never assumed
- Accounting remains grounded

Zero is not the absence of success.

It is the absence of distortion.

## Appendix D — LOOP Accounting, Supply Rules, and Floor Mechanics

This appendix defines LOOP strictly as an accounting construct representing verified retained surplus produced by completed cycles.

LOOP is not yield, not a reward, not a promise, and not a market instrument.  
It exists solely to preserve historical accounting truth.

---

### D.1 Definition of LOOP

LOOP represents **verified retained surplus**.

Surplus qualifies for LOOP representation only if:
- A cycle has completed
- Settlement has occurred
- Verified profit exists
- A portion of that profit is retained by the system

If any condition is not met, LOOP is not created.

---

### D.2 What LOOP Is Not

LOOP does not:
- Guarantee future profit
- Represent unrealized value
- Confer governance rights
- Entitle holders to yield or dividends
- Imply redemption at any price

Absent explicit, future-defined mechanisms, LOOP has no claim function.

---

### D.3 Supply Initialization and Growth

LOOP supply:
- Begins at zero
- Can increase only when new verified surplus is retained
- Cannot be pre-minted
- Cannot be emitted on a schedule
- Cannot be inflated to incentivize behavior

If no surplus is retained, LOOP supply remains unchanged.

---

### D.4 Retained Surplus Rules

Retained surplus is defined as:
- Verified profit remaining after fees and obligations
- Explicitly designated for retention by the system
- Not immediately distributed or consumed

Retention:
- Is prospective
- Is configurable by governance
- Applies only after settlement
- Cannot be reversed retroactively

---

### D.5 The Accounting Floor

The accounting floor is defined conceptually as:

> Total retained verified surplus ÷ LOOP supply

The floor:
- Reflects historical accounting reality
- Is not a market price
- Is not a redemption guarantee
- May stagnate or remain unchanged indefinitely

If no new surplus is retained, the floor does not move.

---

### D.6 Floor Stagnation and Decline

The accounting floor:
- May stagnate during zero-result cycles
- May remain flat for extended periods
- Does not imply underperformance or failure

The floor does not decline due to market price movement, as it is not a price.

---

### D.7 No Feedback Into Execution

LOOP has no influence on:
- Strategy selection
- Capital allocation
- Execution behavior
- Risk exposure
- Cycle authorization

Execution does not optimize for LOOP creation.

---

### D.8 Accounting Integrity

LOOP records:
- Only finalized outcomes
- Only verified retained surplus
- Only post-settlement truth

If surplus is later consumed or reallocated:
- LOOP supply does not retroactively change
- Historical accounting remains intact

---

### D.9 Future Extensions

Any future functionality involving LOOP must:
- Be explicitly defined
- Respect all system invariants
- Apply prospectively only
- Avoid implied guarantees

Absent such definition, LOOP remains a passive accounting record.

---

### D.10 Why LOOP Exists

Most systems lose accounting truth over time.

LOOP exists to preserve it.

It ensures that when surplus occurs:
- It is recorded
- It is auditable
- It cannot be rewritten

LOOP does not promise success.

It records when success actually happened.

## Appendix E — Time, Cycles, Cutoffs, and Authorization Windows

This appendix defines all time-based rules governing cycle authorization, execution duration, settlement timing, and cutoff behavior.

Time constraints are enforced to guarantee finality, prevent ambiguity, and ensure that execution cannot drift indefinitely.

---

### E.1 Time as a Hard Constraint

Time in YieldLoop is not advisory.

All cycles:
- Are explicitly time-bounded
- Have a defined start and end
- Must terminate regardless of execution state

Time limits cannot be extended mid-cycle.

---

### E.2 Cycle Authorization Window

A cycle may be authorized only when:
- The vault is in an **Idle** or **Configured** state
- No pause or emergency restriction is active
- All required parameters are valid

Authorization:
- Fixes the cycle start time
- Locks the execution window
- Commits the vault to execution eligibility

Authorization does not guarantee execution will occur.

---

### E.3 Execution Duration

Each cycle defines a maximum execution duration.

Execution duration:
- Begins at cycle start
- Ends at the earlier of:
  - The configured cycle end time
  - Strategy halt or failure
  - System-enforced termination

Execution may stop early.
Execution may not exceed the defined duration.

---

### E.4 Cutoff Enforcement

At cycle end:
- All strategy execution must stop
- No new actions may be initiated
- Outstanding operations must resolve or fail

Cutoffs are absolute.

There is no grace period, rollover, or continuation.

---

### E.5 Settlement Timing

Settlement begins immediately after execution ends.

Settlement:
- Must begin within a bounded time window
- Cannot be delayed for optimization
- Cannot be paused once started
- Must complete deterministically

If settlement cannot complete within defined bounds, conservative resolution applies.

---

### E.6 Retry and Reentry Rules

Retries during execution are prohibited unless:
- Explicitly authorized in strategy definitions
- Bounded by time and count
- Deterministic

Retries during settlement are prohibited.

Failed settlement does not restart execution.

---

### E.7 Time Source and Drift

Time references must be:
- On-chain
- Deterministic
- Resistant to manipulation within reasonable bounds

If time drift or ambiguity is detected:
- Execution halts
- Settlement resolves conservatively
- Profit is rejected

---

### E.8 Pauses and Global Time Controls

Governance or administration may impose time-based pauses that:
- Prevent new cycle authorization
- Do not affect active execution
- Do not alter settlement behavior

Pauses are:
- Prospective only
- Auditable
- Time-bounded where possible

---

### E.9 Long-Duration and No-Execution Cycles

A cycle may complete without executing any strategy actions.

Such cycles:
- Proceed to settlement
- Resolve to zero
- Close normally

No minimum activity level is required.

---

### E.10 Why Time Is Enforced

Time constraints ensure that:
- Risk exposure is bounded
- Accounting is finite
- Responsibility is clear
- Finality is unavoidable

If execution could run indefinitely, truth would never be forced.

Time is the mechanism that makes outcomes real.

## Appendix F — Execution Engine & Trade Strategy Specifications

This appendix defines the execution engines and strategy classes permitted within YieldLoop, along with their mandatory constraints.

All strategies are execution mechanisms, not decision-makers.  
They operate only within explicitly authorized bounds and never justify, rescue, or reinterpret outcomes.

---

### F.1 Strategy Classes (Authoritative)

YieldLoop currently supports the following strategy classes:

1. **Directional Trading Strategies**  
2. **Arbitrage Strategies**  
3. **Yield Farming Strategies**  
4. **Stable Asset Staking Strategies**  

Additional strategy classes may be introduced in the future only through prospective governance approval and appendix updates.

---

### F.2 Directional Trading Strategies

Directional trading strategies are based on explicit price action rules.

These include, but are not limited to:
- Buy-low / sell-high execution
- Fixed-entry and fixed-exit strategies
- Percentage-based take-profit strategies (e.g., sell at +10–20%)
- Grid-based trading
- Martingale-style position scaling (bounded and explicitly authorized)

Directional strategies must:
- Define entry price logic
- Define exit price logic
- Define maximum exposure
- Define loss limits or halt conditions
- Operate entirely within a single cycle

Directional strategies may not:
- Adapt dynamically beyond predefined rules
- Increase risk beyond authorized bounds
- Roll positions into subsequent cycles
- Override cutoff or settlement rules

If exit conditions are not met by cycle end, the strategy halts and the vault may retain the position as inventory. No profit is recognized unless value is realized into the settlement asset at or before settlement.

---

### F.3 Arbitrage Strategies

Arbitrage strategies exploit price discrepancies across defined venues or pools.

Arbitrage strategies:
- Execute only across explicitly allowlisted routes
- Require deterministic pricing inputs
- Must resolve within the cycle window
- Must halt immediately if the arbitrage spread collapses

Arbitrage strategies may not:
- Assume liquidity
- Chain arbitrage indefinitely
- Retry beyond bounded limits
- Introduce leverage or borrowing

If execution cannot complete deterministically, settlement resolves conservatively.

---

### F.4 Yield Farming Strategies

Yield farming strategies allocate capital to yield-generating mechanisms for the duration of a cycle.

Yield farming strategies must:
- Use explicitly allowlisted protocols
- Define exposure and duration limits
- Exit positions fully before or at cycle end
- Include all rewards in settlement accounting

Yield farming strategies may not:
- Compound implicitly
- Rely on emissions masking losses
- Roll positions across cycles
- Assume future rewards

All yield must survive settlement to count.

---

### F.5 Stable Asset Staking Strategies

Stable asset staking strategies allocate capital to mechanisms intended to preserve value while earning yield.

These strategies:
- Operate only on stable or stability-targeted assets
- Prioritize capital preservation
- Are bounded by exposure and duration
- Are subject to the same settlement rules as all strategies

Stable staking does not imply:
- Guaranteed returns
- Risk-free execution
- Immunity from zero-result cycles

If yield does not survive costs and settlement, the outcome is zero.

---

### F.6 Capital Access and Isolation

All strategies:
- May access only explicitly allocated capital
- May not borrow from other strategies or vaults
- May not access system-owned funds unless explicitly authorized

Capital isolation is mandatory and enforced at all times.

---

### F.7 Prohibited Strategy Behaviors

No strategy may:
- Use leverage
- Borrow or lend assets
- Enter derivatives or margin positions
- Short assets
- Perform flash loans
- Rehypothecate capital
- Modify parameters mid-cycle

Any prohibited behavior triggers immediate halt and settlement.

---

### F.8 Halt and Failure Conditions

A strategy must halt immediately if:
- Price moves outside authorized bounds
- Slippage exceeds defined limits
- Liquidity conditions fail
- External calls revert
- Time cutoffs are reached
- Any invariant is violated

Halt results in immediate transition to settlement.

---

### F.9 Strategy Approval and Evolution

Strategies are approved prospectively by governance.

Governance may:
- Approve new strategy classes
- Retire strategies for future cycles
- Modify allowable parameter ranges

Active strategies within a cycle are never affected.

---

### F.10 Future Strategy Growth

YieldLoop explicitly allows for future strategy expansion.

Any new strategy must:
- Fit within the cycle-based execution model
- Respect all settlement and finality rules
- Be bounded, deterministic, and auditable
- Be documented in a future appendix revision

No strategy is permitted by implication.

---

### F.11 Why Strategy Scope Is Narrow

YieldLoop does not pursue performance through complexity.

By limiting strategies to explicit, bounded behaviors:
- Risk remains visible
- Failure remains bounded
- Accounting remains truthful
- Growth remains optional

Strategies may evolve.

Finality does not.

---

## Appendix G — Fee Structure, Discounts, and Allocation Boundaries

This appendix defines the current platform fee configuration, discount mechanisms, and fee allocation structure.

All fee behavior is **prospective**, **configurable**, and **non-guaranteed**.  
Fees apply only after verified profit is established through settlement.

---

### G.1 When Fees Apply

Platform fees apply **only** when a cycle produces verified profit at settlement.

If a cycle resolves to zero:
- No fee is charged
- No allocation occurs
- No obligation is created

Fees are never charged on:
- Principal
- Unrealized gains
- Estimated or projected value

---

### G.2 Fee Basis

Fees are calculated as a percentage of **net verified profit**.

Rules:
- Fees cannot exceed verified profit
- Fees are assessed only at settlement
- Fees cannot be applied retroactively
- Fees cannot be modified mid-cycle

If settlement rejects profit, the platform fee is zero.

---

### G.3 Current Platform Fee (Default Configuration)

At the time of this document, the platform fee is configured as:

- **20% of net verified profit**

This configuration:
- Applies only to cycles authorized under this setting
- May be modified prospectively by governance or authorized administration
- Does not affect active or settled cycles

There is no guaranteed or permanent fee rate.

---

### G.4 Current Fee Allocation Categories (Default Split)

Collected platform fees are currently allocated across the following categories:

1. **Development**  
   Ongoing protocol development, maintenance, audits, tooling, and engineering work.

2. **Marketing and Ecosystem Growth**  
   Outreach, education, partnerships, and user acquisition activities.

3. **Platform Deposit**  
   System-owned participation conducted under the same execution, cycle, and settlement constraints as user vaults.

4. **LoopLab or Other “Proof of Impact™” Activities**  
   Research, experimentation, public-good initiatives, nonprofit or quasi-nonprofit activity, and long-term impact-oriented development aligned with the Proof of Impact™ framework.

The percentage allocation to each category:
- Is configurable
- Applies prospectively only
- May evolve over time
- Creates no entitlement or guaranteed funding level

These categories define **use-of-funds**, not obligations.

---

### G.5 Discounts and Preferential Rates

The protocol may offer **prospective fee discounts** to certain user classes, including but not limited to:

- Whitelisted supporters
- Governance participants

Discounts:
- Reduce the platform’s share of verified profit
- Apply only to future cycles
- Are disclosed prior to authorization
- Cannot alter settlement math
- Cannot convert a zero-result cycle into a fee-bearing cycle

Discount eligibility is enforced through access control mechanisms defined elsewhere.

---

### G.6 Governor and Contributor Pools

A portion of platform-earned surplus may be designated from the above allocation categories to support:

- Governance participation
- Contributor bounties
- Advisory or operational roles

Such pools:
- Are funded only from verified profit
- Do not exist in zero-result cycles
- Confer no claim on user funds
- Do not influence execution or settlement behavior

Distribution mechanics are defined separately and prospectively.

---

### G.7 Transparency and Auditability

All fee assessments and allocations:

## Appendix J — Security Model, Threat Boundaries, and Assumptions

This appendix defines the security posture of YieldLoop, including explicit threat boundaries, in-scope risks, and out-of-scope assumptions.

YieldLoop is designed to **limit blast radius**, not eliminate risk.

---

### J.1 Security Philosophy

YieldLoop assumes:
- Software can fail
- Dependencies can break
- Markets can behave irrationally
- Users can make mistakes

The system prioritizes:
- Bounded exposure
- Deterministic resolution
- Clear responsibility
- Minimal implicit trust

---

### J.2 In-Scope Threats

The following threats are considered **in scope** and explicitly mitigated where possible:

- Smart contract bugs
- Strategy logic failure
- Oracle or pricing ambiguity
- External protocol failure
- Gas price spikes
- Execution race conditions
- Partial transaction failure
- Malicious external protocol behavior

Mitigations include:
- Capital isolation
- Strategy halting
- Conservative settlement
- Time cutoffs
- Explicit allowlists

---

### J.3 Out-of-Scope Threats

The following are **explicitly out of scope**:

- Global blockchain failure
- Consensus attacks
- Nation-state censorship
- Wallet compromise
- User key loss
- Fiat provider insolvency
- UI or frontend spoofing
- User misunderstanding of risk

These risks are disclosed but not mitigated by protocol logic.

---

### J.4 Trust Boundaries

YieldLoop enforces strict trust separation:

- Users trust only their own wallets
- Strategies trust only defined parameters
- Settlement trusts only verifiable state
- Governance trusts only prospective configuration

No component has unilateral authority over outcomes.

---

### J.5 Administrative Authority Limits

Administrators may:
- Pause new cycle authorization
- Manage infrastructure
- Update non-execution components

Administrators may not:
- Move user funds
- Modify active cycles
- Override settlement
- Alter finalized outcomes

---

### J.6 Dependency Risk

External dependencies are unavoidable.

YieldLoop mitigates dependency risk by:
- Allowlisting protocols
- Bounding execution time
- Halting on failure
- Resolving conservatively

No dependency is assumed reliable.

---

### J.7 Incident Response

In the event of an incident:
- Active execution may halt
- Settlement proceeds conservatively
- New authorization may pause
- No retroactive changes occur

Incident response never rewrites history.

---

### J.8 No Insurance or Guarantees

YieldLoop provides:
- No insurance
- No loss protection
- No performance guarantees
- No implied safety beyond defined constraints

Risk is real and unavoidable.

---

### J.9 Why Security Is Explicitly Limited

Security claims fail when boundaries are unclear.

YieldLoop defines limits so that:
- Risk is visible
- Responsibility is clear
- Failures are survivable
- Trust is not implied

If a risk is not mitigated here, it is not mitigated at all.

## Appendix L — Glossary of Canonical Terms

This appendix defines authoritative meanings for all core system terms.

If a term is used inconsistently elsewhere, this glossary prevails.

---

**Cycle**  
A fixed-duration execution window with enforced settlement and finality.

**Vault**  
A user-controlled container that holds assets and authorizes execution.

**Settlement**  
The deterministic accounting process that finalizes a cycle.

**Finality**  
The irreversible closure of a cycle after settlement.

**Zero-Result Cycle**  
A cycle that produces no verified surplus.

**Verified Profit**  
Positive net outcome surviving settlement and cost deduction.

**LOOP**  
An accounting representation of retained verified surplus.

**Accounting Floor**  
Historical ratio derived from retained surplus and LOOP supply.

**Strategy**  
A bounded execution mechanism operating within a cycle.

**Authorization**  
User approval that locks parameters for a cycle.

**Execution Engine**  
The component responsible for performing strategy actions.

**Whitelisting**  
Role-based access assignment without tokenization.

**Governor**  
A role with prospective configuration influence only.

**Prospective**  
Applying only to future cycles.

**Conservative Resolution**  
Default resolution when ambiguity exists, resulting in zero outcome.
